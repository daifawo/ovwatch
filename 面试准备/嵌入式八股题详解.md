# Part 1　RTOS

## R1. 什么是任务？任务由哪几部分组成？

**结论**：任务 = 一段永不返回的循环代码 + 一份私有栈 + 一个 TCB（任务控制块）。

**展开**：
- **代码**：`void Task(void *arg) { while(1) { ... } }`，正常路径上不返回；返回等于任务结束。
- **私有栈**：保存函数调用链、局部变量，以及切换时压入的 CPU 现场（R0–R15、xPSR 等）。
- **TCB**：FreeRTOS 的 `TCB_t`，记录栈顶指针、任务状态、优先级、事件列表项、通知值、栈起始地址等。调度器切换任务，本质是**换 TCB 里的栈指针**。

**追问**：任务和线程的区别？→ 在 MCU 上没有进程/地址空间隔离，FreeRTOS 的 task 就是线程，所有任务共享同一地址空间。

**项目** 🎯：13 个任务各自有独立 `osThreadAttr_t`，`stack_size` 以**字节**为单位，例如 `128 * 24` = 3072 B。

## R2. 任务有哪几种状态？什么时候切换？

**结论**：Running / Ready / Blocked / Suspended 四种。

**展开**：
- **Running**：正在占用 CPU，单核同一时刻只有一个。
- **Ready**：万事俱备，只差 CPU。同优先级任务一起排队。
- **Blocked**：在等事件或超时（`osDelay`、等队列、等事件组、等信号量）。**有超时时间，可被事件提前唤醒**（但 `osDelay` 等的是时间，不能被事件唤醒）。
- **Suspended**：`vTaskSuspend` 主动挂起，**不参与调度**，只能被 `vTaskResume` 或 `xTaskResumeFromISR` 唤醒，超时对它无效。

**切换时机**：
1. 任务主动阻塞（`osDelay` / 等队列）；
2. 被更高优先级任务抢占；
3. 同优先级时间片用完（`configUSE_TIME_SLICING`）；
4. 任务主动 `taskYIELD()`；
5. 中断退出时触发 PendSV（`portYIELD_FROM_ISR`）。

**追问**：SysTick 和 PendSV 的分工？→ SysTick 只负责“到点了，标记需要调度”；PendSV 设为最低优先级，在所有中断处理完后才做真正的上下文切换，避免在中断里切栈。

**项目** 🎯：`osDelay` 让出的任务只等时间；而等 `osMessageQueueGet`、`osEventFlagsWait` 的任务可以被事件提前唤醒——这是“轮询 vs 阻塞”的核心区别。

## R3. 为什么每个任务要独立栈？栈里放什么？

**结论**：因为切换任务时，CPU 现场和函数调用链必须各存各的，不能互相覆盖。

**展开**：
- 栈里放：函数局部变量、返回地址、入参、以及**上下文切换时压入的寄存器现场**。
- 如果共享一个栈，A 任务执行到一半被 B 抢占，B 的调用链会覆盖 A 的数据，切回来就崩了。
- 代价：RAM。13 个任务 = 13 份栈，这是 RTOS 相对裸机的主要内存开销。

**追问**：栈大小怎么估？→ 先按经验给，再用 `uxTaskGetStackHighWaterMark()` 看历史最低剩余量，留 20%~30% 余量。不能只看“编译通过”。

**项目** 🎯：LVGL 任务 `128*24`（3 KB，调用链深、局部变量多），喂狗任务 `128*1`（512 B，只调用简单函数）。

## R4. FreeRTOS 的调度策略是什么？

**结论**：**抢占式优先级调度 + 同优先级时间片轮转**。

**展开**：
- `configUSE_PREEMPTION = 1`：高优先级任务一旦就绪，立刻抢占当前任务。
- `configUSE_TIME_SLICING = 1`：同优先级任务按 tick 轮流跑，防止饿死。
- 调度器每次选“就绪态里优先级最高的任务”；同优先级取等待最久的（FIFO）。
- 空闲任务（Idle Task）优先级最低，负责回收被删除任务的栈和内存。

**追问**：为什么空闲任务必须存在？→ 保证 CPU 永远有任务可跑；`vTaskDelete(NULL)` 删除自己后，栈由空闲任务回收。

## R5. 优先级数值越大越高还是越低？

**结论**：**FreeRTOS 里数值越大优先级越高**；**CMSIS-OS 的 `osPriority_t` 枚举也是数值越大越高**；但 **Cortex-M 的 NVIC 中断优先级数值越小越高**。两者方向相反，是经典混淆点。

**展开**：
- `osPriorityLow = 8`，`osPriorityLow1 = 9`，…… `osPriorityLow7 = 15`；`osPriorityNormal = 24`；`osPriorityHigh = 32`；`osPriorityHigh1 = 33`……
- 所以 `osPriorityLow2 > osPriorityLow1`，**Low2 比 Low1 高**，名字里的数字容易误导。
- FreeRTOS 内部把 CMSIS 枚举映射成 0~`configMAX_PRIORITIES-1`，数值大的优先。

**追问**：那 `osPriorityRealtime` 呢？→ 最高普通优先级之一（48），高于 High 系；`osPriorityISR` 是保留值，任务不能用。

**项目** 🎯：`Low1` 与 `Low2` 谁高？Low2 高。本项目 `MPUCheckTask`、`DataSaveTask` 是 Low2，`SensorDataTask`、`HRDataTask` 是 Low1，所以抬手检测和存数据优先于传感器刷新——符合“先保证能睡、再保证数据新”。

## R6. 什么是优先级反转？怎么解决？

**结论**：低优先级任务持有锁，高优先级任务等锁，中优先级任务又抢占了低优先级任务，导致高优先级被“间接”阻塞。

**展开**：
1. 低优先级 L 拿到互斥量，开始干活；
2. 高优先级 H 就绪，要同一把锁，阻塞；
3. 中优先级 M 就绪，抢占 L（L 此时还没释放锁）；
4. H 被 M 拖着，等待时间不可预期。

**解决**：
- **优先级继承**（FreeRTOS 互斥量默认）：L 持锁期间临时提升到 H 的优先级，尽快释放。
- **优先级天花板**：持锁时直接提到所有可能使用该锁任务的最高优先级。
- **关调度/关中断**：临界区短时可用，长临界区不可取。

**追问**：二值信号量有优先级继承吗？→ **没有**。只有互斥量（`xSemaphoreCreateMutex`）有，因为它记录了 owner。

**项目** 🎯：本项目几乎不用互斥量，靠“单写者 + 队列”避免共享资源争用；这是取舍，不是没有风险（见 R11、X3）。

## R7. 队列、信号量、互斥量、事件组、任务通知有什么区别？

**结论**：看三个维度——**传不传数据、有没有所有权、能不能一对多**。

| 机制 | 传数据 | 所有权/继承 | 一对多 | 典型用途 |
|---|---|---|---|---|
| 消息队列 | 是（值拷贝） | 无 | 多生产者/多消费者 | 按键事件、传感器数据 |
| 二值信号量 | 否（只计数 0/1） | 无 | 多 | ISR 通知任务、任务同步 |
| 计数信号量 | 否（0~N） | 无 | 多 | 资源计数、事件累计 |
| 互斥量 | 否 | **有**，支持优先级继承 | 多 | 保护共享资源 |
| 事件组 | 否（32 位标志） | 无 | **可一对多、可等多个位** | 多个中断汇聚到一个任务 |
| 任务通知 | 是（32 位值） | 无 | **只能一对一** | 轻量同步，最快 |

**展开**：
- 队列是**拷贝语义**：放进去的是数据副本，发送方栈上的变量可以立刻复用。
- 事件组适合“或/与”等待：`osEventFlagsWait(..., osFlagsWaitAny, ...)` 等任意一个，`osFlagsWaitAll` 等全部。
- 任务通知省一次对象创建和链表操作，速度约快 45%，但一个任务只有一个通知值，多对一时会覆盖。

**项目** 🎯：按键→页面用**队列**（要传键值）；UART IDLE、充电插拔、IMU 中断用**事件组**（多个中断汇聚、只关心“发生过”）。

## R8. 消息队列内部是怎么实现的？

**结论**：一块固定大小的环形缓冲区 + 两个等待列表（发送等待、接收等待）。

**展开**：
- 创建时指定**消息个数**和**每条消息字节数**，内存一次分配好，运行期不再 malloc。
- 发送：拷贝数据进环形缓冲；若满，发送任务按超时阻塞进“发送等待列表”。
- 接收：从缓冲拷出；若无数据，接收任务阻塞进“接收等待列表”。
- 有数据到达时，唤醒等待列表中**优先级最高**的任务（同优先级 FIFO）。
- ISR 版本 `xQueueSendFromISR` 不阻塞，返回 `xHigherPriorityTaskWoken`，退出中断时触发 PendSV。

**追问**：队列深度为 1 会怎样？→ 只能存一条，生产者比消费者快时后到的消息被丢弃或阻塞。

**项目** 🎯：本项目六个队列深度几乎都是 1（`osMessageQueueNew(1, 1, NULL)`），语义是“只关心最新状态”；连按两下键可能丢一次，这是设计取舍。

## R9. 事件组的工作原理？和全局标志位轮询有什么本质区别？

**结论**：事件组是内核对象，任务**阻塞等待**；全局标志是内存变量，任务**循环查询**。前者让出 CPU，后者空转。

**展开**：
- 一个事件组本质是 32 位（`EventBits_t`）标志，每个 bit 独立。
- 等待时可指定“任意一位”或“全部位”，还可设置“等待成功后自动清位”。
- 多个任务可以同时等同一个事件组，置位时所有满足条件的任务都会被唤醒（这是它比信号量强的地方）。
- 中断里可以置位（`osEventFlagsSet` 有 ISR 安全版本），但要注意中断优先级约束（见 R11）。

**追问**：事件组能传数据吗？→ 不能，只能表达“发生了什么”。要带数据就配一个全局变量 + 事件组做同步（本项目 `HardInt_receive_str` 就是这种模式）。

**项目** 🎯：`HardIntEventHandle` 一个事件组同时承载 `HARDINT_EVENT_UART`、`HARDINT_EVENT_CHARG`，不同任务各等各的位，互不干扰。

## R10. 为什么 ISR 里不能调用普通 RTOS API？`FromISR` 做了什么？

**结论**：普通 API 会**阻塞当前任务**，而中断上下文没有“当前任务”可挂起；`FromISR` 版本不阻塞，只返回“是否需要切换”。

**展开**：
- 普通 API 内部可能调用 `vTaskSuspendAll`、把自己挂到等待链表、触发调度——这些都需要一个合法的 TCB。
- 中断里没有任务上下文，栈是 MSP（主栈），不是任务栈；一旦挂起，调度器无从恢复。
- `FromISR` 版本：只操作内核数据结构，不阻塞；通过 `pxHigherPriorityTaskWoken` 告诉调用者“有更高优先级任务被唤醒”。
- 中断退出前调用 `portYIELD_FROM_ISR(xHigherPriorityTaskWoken)`，触发 PendSV，在中断全部结束后再切换。

**追问**：ISR 里能调用 `osDelay` 吗？→ 绝对不能；`HAL_Delay` 也不行，它基于 SysTick 轮询，会卡死整个中断系统。

**项目** 🎯：`USART1_IRQHandler` 里只调 `osEventFlagsSet`（CMSIS-OS 的 ISR 安全实现），不在中断里解析数据、不打印、不延时。

## R11. `configMAX_SYSCALL_INTERRUPT_PRIORITY` 是什么？为什么它决定了 ISR 能不能调 API？

**结论**：它是“允许调用 RTOS API 的中断优先级门槛”。**Cortex-M 数值 ≥ 它的中断才可以调 API**（数值越大优先级越低）。

**展开**：
- FreeRTOS 临界区不是关掉所有中断，而是把 `BASEPRI` 设成 `configMAX_SYSCALL_INTERRUPT_PRIORITY`。
- 优先级数值 **≥** 该值的中断会被 `BASEPRI` 屏蔽（进入临界区时不响应），所以它们可以安全地调 API——因为内核数据结构不会被它们打断。
- 优先级数值 **<** 该值的中断“高于”RTOS，临界区屏蔽不了它们；如果它们调 API，可能在临界区中间破坏内核链表。
- 典型值：`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`，配合 4 位优先级。

**追问**：那高优先级中断要调 API 怎么办？→ 只能把优先级降到 ≥5，或者用“置标志 + PendSV/软中断”转交。没有第三种办法。

**项目** 🎯：本项目 EXTI 原来配成 0（高于 5），在 ISR 里调 `osEventFlagsSet` 是真实隐患，改成 5 才安全（commit `acce748`）。

## R12. 临界区的两种实现有什么区别？

**结论**：`taskENTER_CRITICAL()` 关到 BASEPRI（只屏蔽 RTOS 管理的中断）；`vTaskSuspendAll()` 只关调度器、不关中断。

**展开**：
- `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()`：设置 BASEPRI，屏蔽优先级 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断；**支持嵌套**（计数器）。
- `vTaskSuspendAll()` / `xTaskResumeAll()`：只让调度器不切换，中断照常响应；临界区可以更长，但期间不能调用会阻塞的 API。
- 选择原则：**保护几行代码用关中断；保护一大段、且不想影响中断延迟用挂起调度器**。

**追问**：临界区里能调用 `osDelay` 吗？→ 不能，关中断/关调度期间调用阻塞 API 会触发断言或死锁。

**项目** 🎯：进 STOP 前用 `vTaskSuspendAll()`，因为要执行一串外设关闭操作，不能长时间关中断（会丢 RTC 唤醒）。

## R13. 栈溢出怎么发现？怎么预防？

**结论**：编译期开 `configCHECK_FOR_STACK_OVERFLOW`，运行期看 `uxTaskGetStackHighWaterMark`。

**展开**：
- **方法 1**：`configCHECK_FOR_STACK_OVERFLOW = 1`，切换时检查栈指针是否越界。
- **方法 2**（更可靠）：创建任务时把栈填满 `0xA5`，切换时检查栈末尾 16 字节是否被改写。
- 溢出时调用 `vApplicationStackOverflowHook(task, name)`，在里面打印任务名并停机/复位。
- **高水位**：`uxTaskGetStackHighWaterMark()` 返回历史最小剩余量（单位是字），调一段时间后看，接近 0 就危险。

**追问**：栈溢出会表现成什么？→ 不一定立刻崩，可能悄悄改掉相邻内存（别的任务的 TCB 或全局变量），表现为“偶发 HardFault”或“某个变量莫名其妙变了”——这是最难查的一类 bug。

**项目** 🎯：本项目没开溢出检测，这是一个可以在面试里主动承认的改进点。

## R14. FreeRTOS 的五种堆管理方案有什么区别？

| 方案 | 分配 | 释放 | 碎片 | 适用 |
|---|---|---|---|---|
| heap_1 | ✅ | ❌ | 无 | 只创建不删除，最简单最安全 |
| heap_2 | ✅ | ✅ | 会 | 已不推荐（不合并相邻块） |
| heap_3 | ✅ | ✅ | 看 libc | 包装标准 `malloc/free`，需要线程安全 |
| heap_4 | ✅ | ✅ | 少（相邻空闲块合并） | **最常用**，首次适配 |
| heap_5 | ✅ | ✅ | 少 | 内存分布在多块不连续区域 |

**追问**：为什么嵌入式不爱用 malloc？→ 碎片不可预测、分配时间不确定、失败处理麻烦。RTOS 里更推荐“静态分配 + 队列/内存池”。

**项目** 🎯：LVGL 的 draw buffer 用的是 `static` 数组，不是 malloc，就是为了 RAM 可预测。

## R15. tickless idle 是什么？为什么本项目没用？

**结论**：空闲时关掉周期 tick、让 MCU 进低功耗，醒来再补算流逝的 tick。

**展开**：
- 普通模式：每 1 ms 一次 SysTick 中断，即使没事干也醒一次，功耗下不去。
- tickless：空闲任务里调用 `vPortSuppressTicksAndSleep()`，关 tick、进低功耗，用低功耗定时器（RTC/LPTIM）在下一个任务到期前唤醒，并补偿 tick 计数。
- 代价：唤醒开销、实现复杂（要考虑中断延迟、tick 补偿误差）。

**追问**：本项目的 STOP 和 tickless 有什么区别？→ tickless 是“空闲时自动睡”，本项目是“应用主动判断该睡了”，并且要手动关背光、串口、触摸、看门狗，所以用 `vTaskSuspendAll` + 手动进 STOP 更可控。

## R16. 死锁的四个必要条件？怎么避免？

**结论**：互斥、占有且等待、不可抢占、循环等待。破坏任意一个即可。

**展开**：
- 互斥：资源不能共享 → 难以破坏。
- 占有且等待：拿一把锁时还去拿另一把 → **一次性申请所有锁**。
- 不可抢占：别人拿着不还 → 用**带超时的获取**（`osMutexAcquire` 设 timeout）。
- 循环等待：A 等 B、B 等 A → **固定加锁顺序**。

**追问**：RTOS 里死锁的表现？→ 相关任务全部永久阻塞，其他任务照跑，看门狗如果独立喂也不会复位——非常隐蔽。

## R17. `vTaskDelay` 和 `vTaskDelayUntil` 的区别？

**结论**：前者是**相对延时**（从现在起等 N tick），后者是**绝对延时**（等到指定时刻）。

**展开**：
- `vTaskDelay(100)`：每次从“当前时刻”起算，任务执行时间会累积成周期漂移。
- `vTaskDelayUntil(&last, 100)`：以固定周期唤醒，执行时间被自动扣除，适合采样、控制循环。
- CMSIS-OS 里对应 `osDelay` 和 `osDelayUntil`。

**项目** 🎯：传感器采样若要求严格周期，应该用 `osDelayUntil`；本项目多数是 `osDelay`，属于“够用”的取舍。

## R18. 任务通知的原理和限制？

**结论**：每个任务自带一个 32 位通知值和一个通知状态，**不需要创建任何对象**，所以最快。

**展开**：
- 发送方：`xTaskNotify()` / `xTaskNotifyGive()`；接收方：`xTaskNotifyWait()` / `ulTaskNotifyTake()`。
- 可当轻量二值信号量、计数信号量、事件标志、甚至传一个 32 位值。
- **限制**：只能一对一（发送方必须知道目标任务句柄）；多对一会覆盖；不能广播。
- 速度比队列快约 45%，省 RAM。

**追问**：为什么快？→ 省掉了队列对象的创建、环形缓冲拷贝和等待链表遍历，直接改目标任务 TCB 里的字段。

---

## R19. 二值信号量和计数信号量有什么区别？

**结论**：二值只有 0/1，用于**同步**；计数是 0~N，用于**计数/资源池**。

**展开**：
- 二值信号量：ISR 里 give，任务里 take；等价于“事件发生了”。
- 计数信号量：每来一个事件 +1，任务每处理一个 -1；适合“缓冲区里有几个数据”“还剩几个资源”。
- 两者都**没有优先级继承**，不能当锁用（当锁用要互斥量）。

**项目** 🎯：本项目用队列 + 事件组覆盖了这两类需求，所以没单独用信号量。

---

## R20. 软件定时器和任务有什么区别？

**结论**：软件定时器由**定时器服务任务**统一回调，回调里不能阻塞；任务有独立栈、可以阻塞。

**展开**：
- 软件定时器：`osTimerNew` + `osTimerStart`，回调在 Timer Service Task 上下文执行，所有定时器共用一个栈。
- 回调里不能调用会阻塞的 API，不能 `osDelay`，要尽快返回。
- 适合周期短、逻辑轻的工作（闪烁 LED、超时检测）。
- 任务适合有阻塞等待、有独立状态机的逻辑。

**项目** 🎯：首页 500 ms 刷新用的是 LVGL 的 `lv_timer`（在 LVGL 任务里跑），不是 FreeRTOS 软件定时器。

---

## R21. 队列满/空时，`timeout` 参数怎么影响行为？

**结论**：`0` = 不等待立即返回错误；`osWaitForever` = 永久阻塞；其他值 = 等 N 个 tick。

**展开**：
- `osMessageQueuePut(q, &msg, 0, 0)`：队列满立刻返回 `osErrorResource`。
- `osMessageQueuePut(q, &msg, 0, osWaitForever)`：队列满就睡，直到有空位——在中断里绝不能用。
- `osMessageQueueGet(q, &msg, NULL, 0)`：没数据立刻返回。
- **返回值必须检查**，否则丢消息无声无息。

**项目** 🎯：本项目多处 `timeout = 1`（等 1 tick），既不完全阻塞也不完全丢弃，是一种折中；但返回值没检查，是隐患。

# Part 2　MCU / STM32

## M1. STM32 从上电到 `main()` 发生了什么？

**结论**：取 MSP → 取复位向量 → `SystemInit()` → 拷贝 `.data`、清零 `.bss` → `__libc_init_array` → `main()`。

**展开**：
1. 上电复位，内核从 **0x08000000** 读第一个字作为 **MSP**（主栈指针）。
2. 从 **0x08000004** 读第二个字作为**复位向量**（`Reset_Handler` 地址），跳过去。
3. `Reset_Handler` 调用 `SystemInit()`：使能 FPU、配置时钟、设置向量表偏移。
4. 把 `.data` 段从 Flash 拷贝到 SRAM（初值存在 Flash）。
5. 把 `.bss` 段清零。
6. 调用 `__libc_init_array`（C++ 全局构造、`__attribute__((constructor))`）。
7. 进入 `main()`。

**追问**：为什么 MSP 存在 Flash 最前面？→ Cortex-M 的向量表固定从地址 0 开始（或 VTOR 指向处），前两项就是 MSP 和复位向量，这是硬件约定。

---

## M2. 向量表是什么？VTOR 在 IAP 里为什么必须改？

**结论**：向量表是“异常/中断入口地址表”；APP 不在 0x08000000 时，必须把 `SCB->VTOR` 指向自己的向量表。

**展开**：
- 向量表前 16 项是内核异常（NMI、HardFault、PendSV、SysTick…），后面是外设中断。
- 复位后 VTOR = 0，硬件从 0x08000000 取表。
- Bootloader 在 0x08000000，APP 在 0x0800C000，APP 的中断向量表也在 0x0800C000。
- 如果 APP 不设 VTOR，发生中断时 CPU 仍去 0x08000000 查表，跳到 Bootloader 的中断处理函数——现象是“APP 一进中断就跑飞”。

**追问**：VTOR 对齐要求？→ 必须是 2 的幂、≥128 字节对齐（实际按表大小对齐，0x0800C000 天然满足）。

**项目** 🎯：`main.c:75` 的 `SCB->VTOR = 0x0000C000U;` 就是干这个的（注意这里写的是偏移，等价于 0x0800C000）。

---

## M3. NVIC 优先级分组是什么？为什么 FreeRTOS 要求特殊配置？

**结论**：4 位优先级可以拆成“抢占优先级 + 子优先级”；FreeRTOS 需要**全部给抢占位**（分组 4），否则内核的优先级比较会出错。

**展开**：
- Cortex-M4 有 4 位优先级（16 级），`NVIC_SetPriorityGrouping(n)` 决定拆分方式：
  - 分组 0：0 位抢占 + 4 位子优先级 → 不能嵌套；
  - 分组 4：4 位抢占 + 0 位子优先级 → 纯抢占，数值小优先。
- 抢占优先级决定**能不能打断**正在执行的中断；子优先级只在同时挂起时决定谁先跑。
- FreeRTOS 内部用优先级数值做比较，如果有子优先级位，比较结果和硬件不一致。

**追问**：优先级数值 0 和 15 谁高？→ **0 最高**，15 最低。别和任务优先级搞混。

**项目** 🎯：`configPRIO_BITS = 4`、`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`，所以 EXTI/USART/RTC 都设成 5，安全且不抢太多。

---

## M4. SysTick 是干什么的？

**结论**：24 位递减计数器，产生周期性中断，是 RTOS 的心跳，也是 `HAL_GetTick()` 的时基。

**展开**：
- 重装载值 = `SystemCoreClock / configTICK_RATE_HZ - 1`，本项目 tick = 1 ms。
- 中断里调用 `xPortSysTickHandler()`，递增 tick 计数、检查延时到期、必要时触发 PendSV。
- 也可用 `HAL_Delay()` 做忙等延时（基于 tick 计数）。
- 注意：`HAL_Delay` 在中断里用会死锁（tick 不涨）。

**追问**：为什么 STOP 模式前要关 SysTick 中断？→ STOP 下内核时钟停了，SysTick 不会再计数；不关的话唤醒后 tick 会出现巨大跳变，延时和超时全部错乱。

**项目** 🎯：进 STOP 前 `CLEAR_BIT(SysTick->CTRL, TICKINT)`，醒来 `HAL_SYSTICK_Config(...)` 重装。

---

## M5. STM32F4 的 Flash 有什么特点？擦写要注意什么？

**结论**：按**扇区**擦除、写前必须擦、只能 1→0、擦写期间总线停顿、寿命约 1 万次。

**展开**：
- F411 512 KB，扇区大小：Sector 0–3 = 16 KB，Sector 4 = 64 KB，Sector 5–7 = 128 KB。
- **写**（program）：只能把 1 写成 0；要写 0xFF 以外的新值必须先擦。
- **擦**（erase）：把整扇区恢复成 0xFF（0 → 1）。
- 擦除时 CPU 从 Flash 取指会被暂停（除非代码在 RAM 里跑），中断响应会延迟。
- 寿命约 10k 次擦写，频繁写 EEPROM 的场景要用外部 EEPROM 或磨损均衡。

**追问**：能按字节擦吗？→ 不能，最小擦除单位是扇区。这是很多人答错的地方。

**项目** 🎯：Bootloader 擦 APP 区是按扇区擦（Sector 3 起），APP FLAG 在 Sector 2。

---

## M6. IAP 的原理？跳转 APP 前要做什么？

**结论**：IAP = 程序自己改写 Flash，然后跳转到新程序。跳转前要**关中断、设 MSP、设 VTOR、跳复位向量**。

**展开**：
1. 解锁 Flash（`HAL_FLASH_Unlock`）；
2. 擦除目标扇区；
3. 按字/半字写入；
4. 上锁；
5. 跳转前：
   - `__disable_irq()` 关全局中断；
   - 关闭已开启的外设（SysTick、串口、DMA），否则新程序初始化会冲突；
   - `__set_MSP(*(uint32_t*)APP_ADDR)` 设主栈；
   - `SCB->VTOR = APP_ADDR` 设向量表；
   - 取 `*(uint32_t*)(APP_ADDR + 4)` 作为复位向量，转成函数指针调用。

**追问**：为什么不直接 `goto`？→ 因为要恢复成“刚复位”的状态：栈、向量表、中断都要重置，否则 APP 用的是 Boot 的栈和中断表。

**项目** 🎯：Boot 32 KB（0x08000000–0x08007FFF），0x08008000 放 `"APP FLAG"`，APP 从 0x0800C000 开始。

---

## M7. STM32 的时钟树怎么理解？

**结论**：HSI/HSE → PLL → SYSCLK → AHB/APB 分频 → 各外设。

**展开**：
- **HSI**：内部 16 MHz RC，精度差但上电即有。
- **HSE**：外部晶振（常见 8 MHz），精度高。
- **PLL**：`PLLM` 分频、`PLLN` 倍频、`PLLP/Q` 分频，输出 SYSCLK。
- F411 最高 **100 MHz**；APB1 最高 50 MHz，APB2 最高 100 MHz。
- 定时器时钟：APB 分频不为 1 时，定时器时钟 = APB × 2。
- 串口波特率、SPI 速率、ADC 采样时间都从这个时钟推导，改时钟必须重算。

**追问**：STOP 唤醒后为什么时钟会变？→ STOP 会关闭 PLL，退出后系统回到 HSI 16 MHz，必须重新 `SystemClock_Config()`。

**项目** 🎯：`user_RunModeTasks.c` 唤醒后立刻重配系统时钟和 SysTick，就是这个原因。

---

## M8. DMA 的原理、限制和使用要点？

**结论**：DMA 在外设和内存之间搬数据，**不占 CPU 但占总线**。

**展开**：
- F4 有 DMA1、DMA2，每个有 8 个 Stream，每个 Stream 可选 8 个 Channel（请求源）。
- 工作模式：**普通模式**（搬完停）、**循环模式**（搬完自动重装，适合 ADC/串口连续采样）。
- 传输宽度可配（字节/半字/字），支持地址自增。
- 中断：半传输、传输完成、传输错误。
- 限制：内存到内存只有 DMA2 支持；DMA 和 CPU 同时访问同一块 SRAM 会争总线，高峰期 CPU 会变慢。

**追问**：DMA 完成中断里能直接处理数据吗？→ 尽量只置标志/给信号量，处理放到任务里，避免长时间占中断。

**项目** 🎯：SPI1 TX 用 DMA 刷屏；USART1 RX 用 DMA + IDLE 收不定长包。两者都是“CPU 不参与搬运”。

---

## M9. HardFault 怎么排查？

**结论**：看**压栈帧 + CFSR/HFSR/MMFAR/BFAR**，定位出错指令和原因。

**展开**：
1. 在 `HardFault_Handler` 里取栈帧：判断用的是 MSP 还是 PSP（看 LR 的 EXC_RETURN 位）。
2. 从栈帧里取 `PC`（出错指令地址）、`LR`（谁调用的）。
3. 读 `SCB->CFSR`：
   - `IACCVIOL`：取指违例（跳到非法地址）；
   - `DACCVIOL`：数据访问违例（空指针）；
   - `UNDEFINSTR`：未定义指令；
   - `INVSTATE`：状态非法（如跳转目标 LSB=0）；
   - `UNALIGNED`：非对齐访问；
   - `DIVBYZERO`：除零。
4. `HFSR` 看是否由其他 fault 升级而来；`MMFAR`/`BFAR` 给出出错地址。
5. 常见根因：空指针、栈溢出、数组越界、函数指针未初始化、在过高优先级 ISR 里调 RTOS API。

**追问**：为什么 HardFault 里不能直接 `printf`？→ 可能栈已损坏、串口中断也被影响；应先把关键寄存器存到全局变量或 RAM，复位后再打印。

---

## M10. 程序的内存分区（.text/.data/.bss/heap/stack）？

**结论**：代码和常量在 Flash，已初始化变量在 Flash+RAM，未初始化变量在 RAM，堆栈在 RAM。

**展开**：
- `.text`：代码，Flash。
- `.rodata`：常量、字符串，Flash。
- `.data`：有初值的全局/静态变量，**初值存 Flash，启动时拷到 RAM**。
- `.bss`：无初值或初值为 0 的全局/静态变量，启动时清零，不占 Flash。
- `heap`：`malloc` 用，向上增长。
- `stack`：向下增长（Cortex-M），启动文件里定义大小。

**追问**：为什么 `.bss` 不占 Flash？→ 它全是 0，启动时直接清零即可，没必要在 Flash 里存一堆 0。

**项目** 🎯：LVGL 双缓冲是 `static lv_color_t buf[...]`，落在 `.bss`，启动清零，不增加 bin 体积。

---

## M11. 独立看门狗（IWDG）和窗口看门狗（WWDG）的区别？

**结论**：IWDG 用独立 LSI 时钟，主时钟挂了也能复位；WWDG 用 APB 时钟，有“喂早了也复位”的窗口限制。

**展开**：
- **IWDG**：时钟源 LSI（约 32 kHz），12 位递减计数器，喂狗即重装；一旦启动只能复位停止。适合“系统整体卡死”检测。
- **WWDG**：时钟源 PCLK1，7 位递减计数器，必须在“窗口期内”喂——太晚复位（超时），太早也复位（说明程序跑太快，可能逻辑异常）。
- 两者都需要在初始化时使能，且看门狗一旦开启无法软件关闭（IWDG）。

**追问**：看门狗能检测所有故障吗？→ 不能，见 X3。

**项目** 🎯：本项目用外部硬件看门狗（WDI 翻转），由 `WDOGFeedTask` 100 ms 喂一次；进 STOP 前必须 `WDOG_Disnable()`，否则睡 2 秒会被复位。

---

## M12. 中断响应过程是怎样的？

**结论**：压栈 8 个寄存器 → 取向量 → 执行 ISR → 出栈恢复。

**展开**：
1. 中断到来，硬件自动压栈 `xPSR, PC, LR, R12, R3, R2, R1, R0`（8 个字）到当前栈（MSP 或 PSP）。
2. 从向量表取 ISR 地址，跳转。
3. 执行 ISR（C 函数入口还会再压一些寄存器）。
4. 返回时用 `EXC_RETURN` 值恢复现场。
- **尾链**（tail-chaining）：一个 ISR 结束立刻处理下一个挂起中断，不重新出栈入栈。
- **迟到**（late arrival）：高优先级中断在压栈过程中到来，直接改取向量，省一次出栈。

**追问**：中断延迟由什么决定？→ 当前指令是否可中断、压栈时间、更高优先级中断的嵌套、临界区长度。

---

## M13. 位带（bit-band）是什么？

**结论**：把某一位映射成一个 32 位字的地址，用普通读写实现原子位操作。

**展开**：
- Cortex-M3/M4 支持两个位带区：SRAM 0x20000000 和外设 0x40000000。
- 别名区公式：`alias = 0x22000000 + (addr - 0x20000000)*32 + bit*4`。
- 好处：读改写由硬件完成，**不会被中断打断**，适合多任务共享的标志位。
- Cortex-M7/M33 部分型号不再支持，移植时要注意。

**追问**：和 `volatile` 位域有什么区别？→ 位域是三条指令（读-改-写），可被打断；位带是硬件原子操作。

# Part 3　外设

## P1. I2C 的物理层有什么特点？

**结论**：两根线（SCL/SDA），**开漏输出 + 上拉电阻**，线与逻辑。

**展开**：
- 开漏：器件只能把线拉低，释放时靠上拉电阻回到高电平。
- 线与：只要有一个器件拉低，整条线就是低——这是仲裁和时钟同步的基础。
- 上拉电阻典型 4.7 kΩ（100 kHz）~ 2.2 kΩ（400 kHz）；阻值太大上升沿变慢，太小功耗大。
- 标准模式 100 kHz，快速模式 400 kHz，快速+ 1 MHz。
- 总线电容限制（400 pF），线太长/挂太多器件会导致边沿变缓。

**追问**：为什么不能用推挽？→ 两个器件一个输出高一个输出低会短路，开漏才能实现线与。

---

## P2. I2C 的起始条件和停止条件？

**结论**：起始 = SCL 高时 SDA 由高变低；停止 = SCL 高时 SDA 由低变高。

**展开**：
- 平时 SCL/SDA 都是高（空闲）。
- **起始（S）**：SCL 保持高，SDA 拉低。所有从机开始监听。
- **停止（P）**：SCL 保持高，SDA 释放变高。总线回到空闲。
- **重复起始（Sr）**：不发停止，直接再发一个起始，用于“写地址→读数据”切换而不释放总线。
- 数据位只在 SCL 低电平期间变化，SCL 高电平期间必须稳定（采样窗口）。

**项目** 🎯：软件 I2C 的 `ConnectionError` 判断，本质就是起始后等 ACK 超时。

---

## P3. I2C 的 ACK/NACK 在第几个时钟？怎么用？

**结论**：第 9 个时钟；从机拉低 SDA = ACK，不拉 = NACK。

**展开**：
- 主机发完 8 位（地址或数据）后释放 SDA，第 9 个时钟采样：
  - SDA 低 → ACK，表示“收到/存在”；
  - SDA 高 → NACK，表示“没收到/不存在/结束”。
- **写**：从机每字节回 ACK。
- **读**：主机收完最后一字节要回 **NACK**，告诉从机“不要再发了”，然后发停止。
- 扫描总线找器件：逐个地址发，有 ACK 就存在。

**追问**：主机发地址没人 ACK 说明什么？→ 器件不存在、地址错、器件没上电、总线被拉死。

**项目** 🎯：`ConnectionError` 标志就是初始化时 ACK 超时置位的，单器件掉线不影响其他器件。

---

## P4. I2C 的 7 位地址和读写位怎么组合？

**结论**：地址 7 位 + 1 位 R/W，组成第一个字节；写 = 0，读 = 1。

**展开**：
- 例如 MPU6050 地址 0x68，写是 `0xD0`，读是 `0xD1`。
- 10 位地址模式：先发 `11110xx` 前缀，再发低 8 位，较少用。
- 地址冲突：同型号器件靠 AD0 引脚改地址。

**追问**：为什么很多驱动代码里地址左移一位？→ 因为 HAL 的 `HAL_I2C_Master_Transmit` 接收的是“已左移的 8 位地址”，软件 I2C 则通常自己拼。

---

## P5. I2C 的时钟同步和仲裁是怎么回事？

**结论**：多主机时靠**线与**实现：SCL 取所有主机中低电平最长的，SDA 谁先发 0 谁赢。

**展开**：
- **时钟同步**：每个主机释放 SCL 后，若别的机器还拉着，SCL 保持低——低电平周期取最长者。
- **仲裁**：主机每发一位都和总线实际电平比较；自己发 1 但总线是 0，说明别人发了 0，自己失去仲裁，立刻退出（转从机或重试）。
- 仲裁不会破坏数据，因为输的一方发的位本来就和总线一致。

**追问**：仲裁和冲突的区别？→ 仲裁是协议内的正常机制，不会丢数据；冲突（两个主机同时发不同数据且都没检测到）不会发生，因为线与必然让一方退出。

---

## P6. 什么是重复起始（Repeated Start）？为什么需要？

**结论**：不发停止，直接再发起始，用于同一次传输里“先写寄存器地址再读数据”。

**展开**：
- 典型读传感器：`Start → 写设备地址(W) → 写寄存器地址 → Repeated Start → 写设备地址(R) → 读数据 → NACK → Stop`。
- 如果中间发 Stop，总线可能被其他主机抢走，寄存器和数据就不是同一次事务了。
- 重复起始保证原子性。

**项目** 🎯：读 MPU6050 的加速度寄存器就是“写地址 → Sr → 读”的流程。

---

## P7. I2C 总线死锁怎么恢复？

**结论**：从机把 SDA 拉死时，主机发 **9 个 SCL 脉冲**让从机把当前字节发完，再发 STOP。

**展开**：
- 现象：SDA 一直为低，主机发不了起始（起始要求 SDA 高）。
- 原因：主机复位时从机正处在“读数据位”状态，一直等时钟。
- 恢复：把 SCL 当普通 GPIO，手动打 9 个脉冲（让从机移出 8 位数据 + 1 位 ACK），然后手动产生 STOP 时序。
- 彻底方案：给从机加复位引脚，或主机侧做超时后重新初始化 I2C 外设。

**项目** 🎯：`iic_bus_t` 里的 STOP 恢复就是这一类处理。

---

## P8. 软件 I2C 和硬件 I2C 有什么区别？

| 维度 | 软件 I2C | 硬件 I2C |
|---|---|---|
| 引脚 | 任意 GPIO | 固定复用引脚 |
| 速度 | 受 CPU 影响，通常 ≤100 kHz | 可达 400 kHz / 1 MHz |
| CPU 占用 | 高（逐位翻转） | 低（DMA 可进一步降低） |
| 灵活性 | 可随意处理异常、多总线 | 受外设状态机限制 |
| 稳定性 | 取决于实现 | STM32 早期硬件 I2C 有勘误，易卡死 |

**追问**：为什么很多开源项目用软件 I2C？→ 引脚自由、移植简单、能绕开硬件外设的勘误和卡死问题。

**项目** 🎯：本项目 7 类器件全挂软件 I2C，就是为了统一抽象和容错。

---

## P9. SPI 的四种模式怎么理解？

**结论**：`CPOL` 决定空闲电平，`CPHA` 决定在哪个边沿采样。

**展开**：
- `CPOL=0`：空闲低；`CPOL=1`：空闲高。
- `CPHA=0`：第一个边沿采样；`CPHA=1`：第二个边沿采样。
- 组合成 Mode 0~3；最常用 **Mode 0**（CPOL=0, CPHA=0）和 **Mode 3**（CPOL=1, CPHA=1）。
- 主从必须配置一致，否则数据错位一位。

**追问**：怎么快速判断用哪个模式？→ 看从机数据手册的时序图：时钟空闲是高还是低、数据在上升沿还是下降沿有效。

**项目** 🎯：ST7789 通常用 Mode 0 或 Mode 3，初始化时 SPI 配置必须和屏一致。

---

## P10. SPI 怎么接多个从机？

**结论**：每个从机一根独立片选（CS），SCK/MOSI/MISO 共享。

**展开**：
- 片选低有效，同一时刻只能拉低一个。
- 也可以用译码器扩展片选。
- 没有片选时，多个从机同时驱动 MISO 会冲突。
- SPI 没有地址，靠片选区分器件——这是它和 I2C 最大的区别。

**追问**：SPI 支持多主吗？→ 标准 SPI 不支持多主；I2C 支持。

---

## P11. SPI + DMA 刷屏的完整流程？

**结论**：设置显示窗口 → 启动 DMA 发送像素 → DMA 完成中断里等 BSY → 通知 LVGL 可以复用缓冲区。

**展开**：
1. 发命令设置行列地址（窗口）；
2. 拉高 DC（数据模式）；
3. `HAL_SPI_Transmit_DMA(buf, len)`；
4. DMA 完成中断：此时数据已搬到 SPI 移位寄存器，但最后 1~2 字节可能还在发；
5. 等 `SPI_FLAG_BSY` 清零；
6. 调用 `lv_disp_flush_ready()`，告诉 LVGL 这块 buffer 可以复用。

**追问**：为什么不能在 DMA 完成瞬间就 ready？→ 会让 LVGL 立刻往同一块 buffer 写下一帧，把还没发完的字节改掉，出现撕裂/花屏。

**项目** 🎯：`HAL_SPI_TxCpltCallback` 里 `while (SR & SPI_FLAG_BSY)` 就是这个等待。

---

## P12. UART 的帧格式和波特率误差？

**结论**：1 起始位 + 5~9 数据位 + 可选校验位 + 1/2 停止位；波特率误差一般要求 < 2~3%。

**展开**：
- 波特率 = `fCK / (16 × USARTDIV)`（过采样 16 时）。
- 误差来源：时钟源精度（HSI 差、晶振好）、分频取整。
- 误差累积到一帧末尾会采错位，所以误差要控制在半个位时间内。
- 常见配置：115200-8-N-1。

**追问**：为什么 HSI 做串口容易乱码？→ 内部 RC 精度约 ±1%，加上分频误差，高温下可能超限；正式产品用外部晶振。

---

## P13. UART 怎么收不定长数据？IDLE 中断的原理？

**结论**：DMA 持续接收 + IDLE 中断判断“一帧结束”，然后处理已收长度。

**展开**：
- 固定长度接收：`HAL_UART_Receive_DMA(buf, len)`，收满才中断——协议长度不定时不适用。
- IDLE 中断：总线连续空闲一个字符时间后触发，表示“这一帧发完了”。
- 流程：DMA 收到 IDLE → 计算已收字节数（DMA 剩余计数）→ 置事件/信号量 → 重新启动 DMA。
- 注意：IDLE 中断里要清标志、要重启 DMA，否则只收一帧。

**项目** 🎯：`USART1_IRQHandler` 里清 IDLE → 置事件组 → `HAL_UART_DMAStop` → 重新 `HAL_UART_Receive_DMA(25)`。

**追问**：25 字节定长 + IDLE 有什么风险？→ 如果对端正好发满 25 字节，缓冲区没有 `\0`，`strcmp` 会越界。

---

## P14. UART 的流控和半双工？

**结论**：硬件流控用 RTS/CTS 防丢数据；半双工用一根线分时收发（如 RS485）。

**展开**：
- **硬件流控**：接收方缓冲区快满时拉高 RTS，发送方暂停。
- **软件流控**：XON/XOFF 字符，简单但会占用数据字节。
- **半双工**：TX/RX 合一，靠方向控制引脚切换（RS485 的 DE/RE）。
- 全双工需要 TX、RX 两根线。

**追问**：BLE 模块通常用哪种？→ 简单透传多用全双工 TTL 串口，不接流控。

---

## P15. ADC 的采样时间为什么重要？

**结论**：采样保持电容需要时间充到被测电压，源阻抗越大、采样时间要越长，否则精度下降。

**展开**：
- ADC 内部有个采样电容，采样阶段通过开关和外部电路连通充电。
- 充电时间常数 = `(R_source + R_internal) × C`；采样时间不够就充不满，读数偏低。
- STM32 可配采样周期（3/15/28/56/84/112/144/480 cycles），周期越多越准但越慢。
- 高阻信号源（如分压电阻很大）要加运放缓冲或加长采样时间。

**追问**：为什么电池电压采集常加电容？→ 降低源阻抗、抗干扰、提供瞬时电荷。

**项目** 🎯：电量采集用 ADC 8 次均值，本质上也是降噪。

---

## P16. ADC 的分辨率、参考电压、校准和多通道？

**结论**：12 位分辨率，参考电压决定量程，多通道用 DMA 扫描，校准消除内部误差。

**展开**：
- 12 位 → 0~4095；`V = adc × Vref / 4095`。
- Vref 可以是 VDDA 或外部基准；VDDA 波动会直接反映到读数。
- **校准**：上电后执行一次，消除内部电容失配。
- **多通道**：规则组扫描 + DMA 循环搬运，一次转换多个通道。
- 过采样可以提升有效位数（硬件过采样或软件平均）。

**追问**：平均能提高精度吗？→ 能降低随机噪声（√N 倍），但对系统性偏差无效。

---

## P17. 定时器的时基和 PWM 怎么配置？

**结论**：`PSC` 分频、`ARR` 定周期、`CCR` 定占空比。

**展开**：
- 计数频率 = `TIM_CLK / (PSC + 1)`。
- 周期 = `(ARR + 1) / 计数频率`。
- 占空比 = `CCR / (ARR + 1)`。
- PWM 模式 1：CNT < CCR 输出有效；模式 2 相反。
- **预装载（ARPE）**：防止运行中改 ARR/CCR 时出现毛刺，更新事件时才生效。

**项目** 🎯：背光调光就是 PWM 改 CCR；长按 3 秒关机在 TIM1 中断里判断。

---

## P18. 输入捕获和编码器模式怎么用？

**结论**：输入捕获测频率/脉宽；编码器模式自动根据 A/B 相计数。

**展开**：
- **输入捕获**：定时器记录边沿到来时的 CNT 值，两次差值 = 周期或脉宽。
- 测频率：单位时间内的边沿数，或两次上升沿差值取倒数。
- 测占空比：上升沿和下降沿各捕获一次。
- **编码器模式**：A/B 两相正交信号，硬件自动加减计数，用于旋钮/电机。

**追问**：捕获溢出怎么办？→ 开更新中断计数溢出次数，或在两次捕获间保证不溢出（选合适 PSC）。

---

## P19. EXTI 是什么？按键消抖有哪几种方式？

**结论**：外部中断控制器，把 GPIO 边沿变成中断/事件；消抖分硬件和软件两种。

**展开**：
- 可配上升沿、下降沿、双边沿触发。
- **中断**会进 ISR；**事件**只触发其他外设（如 ADC、DMA），不进 ISR，功耗更低。
- 消抖：
  - 硬件：RC 低通、施密特触发器；
  - 软件：延时重采样（简单但阻塞）、状态机/计数器（推荐）、定时器扫描。
- 机械按键抖动通常 5~20 ms。

**项目** 🎯：`KeyScan` 用“按下-松开”状态机 + 3 ms 延时，松开才返回键值；EXTI 只用于 STOP 唤醒。

---

## P20. RTC 的时钟源、备份域和唤醒定时器？

**结论**：通常用 LSE 32.768 kHz，备份域由 VBAT 供电，可做闹钟和周期唤醒。

**展开**：
- **LSE**：外部 32.768 kHz 晶振，精度高、功耗低；也可用 LSI（内部，精度差）。
- **备份域**：VBAT 引脚供电，主电源掉电后 RTC 和备份寄存器继续走。
- **闹钟**：指定时分秒或日期触发中断。
- **唤醒定时器**：按固定周期唤醒（本项目的 2 s），无需设置具体时间。
- 首次配置后要写备份寄存器标记，避免每次复位都重新初始化（否则时间被重置）。

**项目** 🎯：`HAL_RTCEx_SetWakeUpTimer_IT` 每 2 秒唤醒一次，醒来判断抬手/按键/充电，不满足就继续睡。

# Part 4　C 语言

## C1. `volatile` 到底保证什么？不保证什么？

**结论**：保证**每次都从内存读/写**，不被编译器优化进寄存器；**不保证原子性**，也不保证内存序。

**展开**：
- 适用场景：中断和主循环共享的变量、硬件寄存器、DMA 缓冲区。
- 不适用：多任务同步（需要临界区/原子操作）。
- 典型错误：`volatile uint32_t flag;` 然后 `flag++`——读、加、写三条指令，中间可被中断打断。
- 在 Cortex-M 上 32 位对齐访问本身是原子的，但 `++` 不是。

**项目** 🎯：`IdleTimerCount` 在 Tick Hook 里 `+=`、在任务里清零，没有原子保护。

---

## C2. `static` 有哪几种用法？

**结论**：三种——文件内可见的全局变量/函数、函数内静态变量、静态局部数组。

**展开**：
- 修饰全局变量/函数 → **内部链接**，只在本文件可见，避免命名冲突。
- 修饰局部变量 → **静态存储期**，只初始化一次，函数返回后值保留。
- 在嵌入式里还常用来把大数组放进 `.bss` 而不是栈（防栈溢出）。
- 注意：静态局部变量**不可重入**，中断和任务同时调用会互相踩。

**项目** 🎯：LVGL 的 `static lv_color_t buf_2_1[...]` 就是放 `.bss`，避免占栈。

---

## C3. `const` 有哪些用法？

**结论**：表示只读，编译器可放 Flash；指针 const 的位置决定“谁不能改”。

**展开**：
- `const int a`：a 不能改。
- `const int *p`：指向的值不能改，指针可改。
- `int * const p`：指针不能改，值可改。
- `const int * const p`：都不能改。
- 嵌入式意义：`const` 数据放 Flash（`.rodata`），省 RAM。

**追问**：`const` 变量能被修改吗？→ 通过强制去 const 的指针可以（未定义行为），但 Flash 里的常量写不进去，会 HardFault。

---

## C4. 指针和数组、函数指针的区别？

**结论**：数组名是地址常量，`sizeof` 不同；函数指针存函数地址，可实现回调/多态。

**展开**：
- `int a[10]`：`sizeof(a) = 40`；`int *p = a`：`sizeof(p) = 4/8`。
- 数组名作函数参数会退化为指针，函数内无法用 `sizeof` 求长度。
- 函数指针：`void (*cb)(int);`，用于回调、状态机表、驱动抽象。
- 函数指针数组可实现“命令表/状态机”。

**项目** 🎯：`HWInterface` 就是一堆函数指针，UI 层通过它调硬件，实现 PC 仿真/真机切换。

---

## C5. 结构体对齐、位域、`__packed` 有什么区别？

**结论**：默认按最大成员对齐（有填充）；位域按位分配；`__packed` 取消填充（可能非对齐访问）。

**展开**：
- 对齐规则：每个成员相对起始地址的偏移是其大小的整数倍；结构体总大小是最大成员的整数倍。
- 例：`char a; int b;` → 大小 8（a 后填充 3 字节）。
- 调整成员顺序可减小体积（大在前）。
- 位域：`unsigned int flag : 1;`，节省空间，但跨平台布局不保证。
- `__packed`：用于协议解析，但访问非对齐成员可能触发 HardFault（M4 部分指令不允许）。

**追问**：什么时候必须 `__packed`？→ 和外部设备/网络协议对接、内存布局必须逐字节一致时。

---

## C6. 大小端是什么？Cortex-M 用哪种？

**结论**：多字节数据在内存里的存放顺序；Cortex-M 默认**小端**。

**展开**：
- 小端：低字节在低地址（0x12345678 → `78 56 34 12`）。
- 大端：高字节在低地址（`12 34 56 78`）。
- 通信协议通常规定大端（网络字节序），需要转换（`htons`/`ntohl`）。
- 判断方法：`union { uint16_t u; uint8_t b[2]; } x = {0x0102};` 看 `b[0]`。

**项目** 🎯：BLE 上报数据时如果按字节打印，要注意协议端序。

---

## C7. 程序的内存分区和变量生命周期？

**结论**：栈（自动）、堆（手动）、`.data`/`.bss`（静态）、`.rodata`/`.text`（只读）。

**展开**：
- 栈：函数局部变量，进入作用域分配、离开释放，向下增长，大小有限。
- 堆：`malloc/free`，手动管理，易碎片。
- 全局/静态：程序整个生命周期。
- 常量/代码：Flash，只读。
- 嵌入式里栈溢出是最常见的崩溃原因之一。

**追问**：局部数组太大放栈上会怎样？→ 栈溢出，可能悄悄改掉别的变量，表现为随机死机。

---

## C8. 什么是可重入函数？怎么保证线程安全？

**结论**：可重入 = 能被多个执行流同时调用而不出错；线程安全还需要保护共享资源。

**展开**：
- 可重入函数：不用全局/静态变量、不返回静态缓冲区地址、不调用不可重入函数。
- 线程安全：可重入是基础，共享资源还要加锁/临界区。
- 不可重入的典型：`strtok`、`printf`（共享输出缓冲）、`malloc`（内部堆锁）。
- 中断里调用不可重入函数 → 数据错乱。

**项目** 🎯：ISR 里只置事件标志，不调 `printf`、不调 `osDelay`，就是为了避免不可重入问题。

---

## C9. 宏、内联函数、`static inline` 的区别？

**结论**：宏是文本替换（无类型检查）；`inline` 建议编译器展开（有类型检查）；`static inline` 限定文件内。

**展开**：
- 宏：预处理阶段替换，可能产生副作用（如 `#define SQ(x) x*x`，`SQ(a+1)` 出错），要用括号包住参数。
- `inline`：编译器决定是否展开，不保证。
- `static inline`：头文件里定义，避免多重定义。
- 嵌入式里小函数用 `static inline` 兼顾效率和类型安全。

---

## C10. 嵌入式常见的未定义行为有哪些？

**结论**：越界访问、空指针解引用、非对齐访问、有符号溢出、野指针、`free` 后使用。

**展开**：
- 数组越界：写到相邻变量/栈帧，表现随机。
- 空指针：HardFault。
- 非对齐访问：M4 上部分指令（如 `LDRD`）会 fault。
- 有符号整数溢出：C 标准是未定义，编译器可能优化掉判断。
- 野指针/重复 free：堆破坏，可能很久后才崩。
- 未初始化变量：`-Wuninitialized` 要开。

**追问**：怎么减少？→ 开 `-Wall -Wextra`、用静态分析、加断言、关键数组加长度检查。

# Part 5　低功耗

## L1. SLEEP / STOP / STANDBY 三种低功耗模式的区别？

**结论**：SLEEP 只停 CPU；STOP 停所有时钟但保留 SRAM/寄存器；STANDBY 全停、SRAM 丢失。

**展开**：
| 模式 | CPU | 时钟 | SRAM/寄存器 | 唤醒 | 电流 |
|---|---|---|---|---|---|
| SLEEP | 停 | 外设可运行 | 保留 | 任意中断 | mA 级 |
| STOP | 停 | 全停 | **保留** | EXTI/RTC | µA~几十 µA |
| STANDBY | 停 | 全停 | **丢失**（除备份域） | WKUP/复位 | 几 µA |

- STOP 唤醒后相当于“时钟全部复位”，必须重新配置系统时钟和外设。
- STANDBY 唤醒等于复位，程序从头跑。

**项目** 🎯：选 STOP 是因为要保留 RAM 里的 UI 状态和任务数据，且要能被 RTC/按键唤醒。

---

## L2. STOP 模式的唤醒源有哪些？唤醒后发生什么？

**结论**：任意 EXTI 线（含 RTC 闹钟/唤醒定时器、按键、充电检测）。

**展开**：
- 进入 STOP 前要确保唤醒源已配置并使能。
- 唤醒后：
  1. 系统时钟恢复为 HSI 16 MHz；
  2. 需要重新 `SystemClock_Config()` 配回 PLL；
  3. SysTick 需要重装；
  4. 外设（串口、LCD、触摸）需要重新初始化。
- 唤醒延迟约几 µs（HSI 起振 + PLL 锁定）。

**项目** 🎯：醒来后 `SystemClock_Config()` → 重装 SysTick → `xTaskResumeAll()` → 判断抬手/按键/充电。

---

## L3. 进入 STOP 前要做哪些准备？

**结论**：关外设、定 IO 电平、关看门狗、关 SysTick 中断、挂起调度器。

**展开**：
1. **关背光、关 LCD、触摸进睡眠**：这些是主要耗电项。
2. **串口 IO 反初始化**：悬空输入引脚会因输入缓冲器翻转而漏电。
3. **关外部看门狗**：否则睡 2 秒会被复位（本项目必须 `WDOG_Disnable()`）。
4. **清 SysTick 中断位**：防止唤醒后 tick 跳变。
5. **`vTaskSuspendAll()`**：防止调度器在关外设过程中切走。
6. 确认所有唤醒源已配置。

**项目** 🎯：`user_RunModeTasks.c` 的 `sleep:` 标签下就是这一整套。

---

## L4. 为什么唤醒后必须重新配置时钟和 SysTick？

**结论**：STOP 会关闭 PLL，退出后系统回到 HSI 16 MHz；不重配的话所有基于时钟的外设（串口波特率、SPI、定时器）全部错乱。

**展开**：
- STOP 下 HSE/PLL 都停了，硬件复位时钟树到默认状态。
- 不重配时钟 → 串口波特率变成原来的 1/6 左右，直接乱码。
- SysTick 重装载值也是按 100 MHz 算的，不重装会导致 tick 周期错。
- 顺序：先配时钟，再配 SysTick，再恢复外设。

**项目** 🎯：`SystemClock_Config()` → `HAL_SYSTICK_Config(...)` → `WDOG_Feed()` → `xTaskResumeAll()`。

---

## L5. 休眠电流怎么测？800 µA 由哪些部分组成？

**结论**：µA 档串联测总电流；主要来自 MCU STOP 电流、LDO 静态电流、外设漏电、上拉电阻。

**展开**：
- 测量：断开调试器（SWD 也会耗电）、万用表 µA 档串在电池和板子之间、等待稳定后读数。
- 组成部分：
  - MCU STOP 模式本身（F411 约几十 µA）；
  - LDO/DC-DC 静态电流（可能几十 µA）；
  - 传感器待机电流（IMU、心率、环境传感器）；
  - IO 悬空/上拉造成的漏电；
  - 背光/触摸未完全关断。
- 优化顺序：先关大项（背光、屏幕），再查 IO 配置，最后看电源芯片。

**项目** 🎯：定位到串口 IO 悬空是主因，反初始化为输入后降到约 800 µA。

---

## L6. 为什么悬空 IO 会漏电？

**结论**：CMOS 输入引脚悬空时电压不确定，输入缓冲器的 NMOS/PMOS 可能同时导通，产生贯穿电流。

**展开**：
- 数字输入是高阻，悬空时电荷积累、电压漂移到阈值附近。
- 阈值附近两个管子都半开，形成从 VDD 到 GND 的直流通路。
- 解决：配成**模拟输入**（关掉输入缓冲）、**输出低/高**、或加**外部上拉/下拉**。
- 同理：未使用的引脚不要留浮空。

**项目** 🎯：`HAL_UART_MspDeInit(&huart1)` 把串口引脚恢复成默认（通常是模拟/浮空），本项目还进一步确认了引脚状态。

# Part 6　高频坑题

## X1. `volatile` 能保证原子性吗？

**不能。** 它只保证每次都从内存读写，不保证读-改-写是一条指令。`volatile uint32_t x; x++;` 是三条指令，可被中断打断。要原子性用临界区、关中断或硬件原子指令（LDREX/STREX）。

## X2. I2C 是全双工还是半双工？

**半双工。** 只有一根数据线 SDA，收发分时进行。**SPI 才是全双工**（MOSI/MISO 独立）。

## X3. 看门狗能防止所有死机吗？

**不能。** 独立喂狗任务只要调度器还在转就一直喂，检测不到：
- 某个任务死锁/饿死；
- UI 卡死但调度器正常；
- 逻辑错误但程序还在跑。

改进：喂狗前检查各任务的“心跳计数器”，或让业务任务轮流喂狗。

## X4. 中断里可以 `printf` 吗？

**不建议。** `printf` 不可重入、可能阻塞很久（串口慢、缓冲区满），会拉长中断、影响实时性，甚至死锁。中断里只置标志，打印放任务里。

## X5. SPI 时钟越高刷屏越快吗？

**不一定。** 受限于：
- ST7789 的最大 SPI 时钟；
- DMA 总线和 CPU 争用；
- 每次刷屏的窗口设置开销；
- 实际瓶颈常在 LVGL 渲染而不是 SPI 传输。

## X6. 中断优先级数值 0 和 15，谁更高？

**0 更高。** Cortex-M 的 NVIC 优先级数值越小越高；这和 FreeRTOS 任务优先级（数值越大越高）方向相反。

## X7. `osDelay(0)` 和 `taskYIELD()` 有什么区别？

- `osDelay(0)`：让出 CPU，进入就绪态，同优先级任务可运行。
- `taskYIELD()`：立刻触发一次调度，如果有同优先级就绪任务就切过去。
- 两者都不会让低优先级任务运行（除非没有更高/同优先级就绪任务）。

## X8. `malloc` 在嵌入式里为什么危险？

**碎片不可预测、分配时间不确定、失败难处理、堆大小难估。** RTOS 里优先用静态分配、内存池、队列。频繁 malloc/free 运行几天后可能突然分配失败。

# 附录　答题模板与抽背规则

## 答题模板（四段式）

被问任何一个八股题，按这个结构答，比背定义更像做过项目：

1. **结论**：一句话给判断（“是/不是”“用 A 不用 B”）。
2. **原理**：为什么（机制、硬件/内核层面）。
3. **代价**：这么做有什么代价（RAM、延迟、复杂度、可靠性）。
4. **实例**：我项目里怎么用的（能报文件/函数/数字最好）。

> 例：问“为什么用事件组不用全局标志？”
> 结论：全局标志要轮询，事件组让任务阻塞。原理：事件组是内核对象，置位时唤醒等待任务；全局标志只能靠 while 循环查。代价：多一个内核对象、32 位位宽限制。实例：UART IDLE 中断置位，`MessageSendTask` 阻塞等，CPU 占用从空转降到 0。

## 抽背规则

1. 报题号（如 R7 / P13），先**不看答案**口述四段式。
2. 对照本文件补缺口，重点补“原理”和“代价”两段。
3. 答错的题记入欠账清单，当天必须重答一次。
4. 连续两轮全对才标记为已掌握。
